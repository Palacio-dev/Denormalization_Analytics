# Phase 1 – Schema Assessment

### Entity Relationships & Cardinalities
The source schema represents a classic **Sales and Returns** domain with two distinct sales channels (Store and Catalog/Web) and one inventory dimension.
1.  **Store Sales Flow**: `s_purchase` (1:1) → `s_purchase_lineitem` (1:N).
2.  **Catalog/Web Sales Flow**: `s_catalog_order` / `s_web_order` (1:1) → respective lineitem tables (1:N).
3.  **Returns Flow**:
    *   Store Returns: `s_purchase` (via `sret_purchase_id`) → `s_store_returns` (1:N).
    *   Catalog Returns: `s_catalog_order` → `s_catalog_returns` (1:N).
4.  **Inventory**: `s_inventory` acts as a snapshot table (1:N with items, N:M with warehouses over time).

### Join Paths & Lookup Tables
*   **Key Lookup Tables**: `s_item_master` (implied by `item_id`), `s_store`, `s_customer`, `s_call_center`, `s_warehouse`, `s_web_site`, `s_promotion`, `s_ship_mode`, `s_ship_date` (dates).
*   **Join Complexity**: The current OLTP schema requires joining multiple tables to get a "Customer Total Spend" or "Store Performance" report. For example, calculating Store Revenue requires joining `s_purchase`, `s_purchase_lineitem`, and potentially `s_inventory` for stock impact.

### Query Access Patterns
*   **Aggregations by Store/Customer/Date**: Sum of sales, average price, quantity sold.
*   **Time-Series Analysis**: Month-over-month growth, trend analysis.
*   **Drill-down**: From Store to Line Item to Item Details.
*   **Return vs. Sale Analysis**: Ratio of returns to sales by reason or amount.

# Phase 2 - Analytical Modeling Strategy

### Chosen Architecture: **Star Schema with Reference Data Absorption**
**Justification**:
1.  **Query Simplicity**: OLAP workloads suffer when joining 4+ tables. A Star Schema allows direct aggregation on Fact tables.
2.  **BI Compatibility**: Tools like Tableau, PowerBI, and Looker expect denormalized dimensions for easy drag-and-drop.
3.  **Performance**: Joining a fact table to a single denormalized dimension table is significantly faster than joining multiple normalized tables.
4.  **Traceability**: While we denormalize, we maintain logical separation by naming conventions (`s_` for store, `c_` for catalog) and include a `source_type` column to allow filtering by business line if needed.

### Denormalization Decisions & Tradeoffs

| Decision ID | Description | Performance Objective | Join Reduction | Redundancy | Maintenance Implication |
| :--- | :--- | :--- | :--- :--- | :--- |
| **D1** | **Absorb Dimensions into Facts**: Move `store_id`, `customer_id`, `item_id`, `promotion_id`, `warehouse_id` from `s_purchase` and `s_purchase_lineitem` into the fact tables. | Eliminates the need to join `s_purchase` and `s_purchase_lineitem` for line-level analysis. | Reduces joins from 2 to 0 for line-item facts. | Stores `store_id` in both `s_purchase` and `s_purchase_lineitem`. | Requires updating both tables on store changes, but this is acceptable in an analytical warehouse where source of truth is the fact table. |
| **D2** | **Create Unified Fact Tables**: Combine `s_catalog_order`/`s_web_order` into `s_orders` and `s_catalog_order_lineitem`/`s_web_order_lineitem` into `s_order_lineitem`. | Unifies logic across channels, allowing "Total Company Revenue" queries without `CASE WHEN` or channel-specific joins. | Reduces joins from 2 to 0 for order-level facts. | Duplicates `order_id` and channel-specific fields (`call_center_id` vs `web_site_id`) into a single fact table. | Requires careful partitioning strategy to handle mixed data types and update frequencies. |
| **D3** | **Flatten Returns**: Merge `s_store_returns` and `s_catalog_returns` into `s_returns`. | Allows a single query to analyze return rates across all channels. | Reduces joins from 2 to 0 for returns facts. | Duplicates return metrics and merges channel-specific fields. | Ensures consistent return logic across the platform. |
| **D4** | **Snapshot Inventory**: Convert `s_inventory` into a Time-Series Snapshot table (`s_inventory_snapshots`). | Enables "Inventory Level on Date X" queries without complex window functions or joins. | Eliminates need to join `s_inventory` with `s_item` or `s_warehouse`. | Stores `item_id` and `warehouse_id` in the snapshot table. | Requires daily incremental loads to maintain accuracy. |

# Phase 3 – Analytical Physical Model Design

### Design Rationale
*   **Fact Tables**: Designed with `date` as the primary grain (or `order_date` for orders, `purchase_date` for sales) to support time-based slicing.
*   **Surrogate Keys**: Integer surrogate keys (`f_id`) are used for Fact tables to optimize indexing and avoid string concatenation issues.
*   **Data Types**: `numeric` is used for monetary values. `date` is normalized to `DATE` type.
*   **Partitioning**: Fact tables are partitioned by `order_date` or `purchase_date` to enable efficient pruning in large datasets.
*   **Clustering**: Fact tables are clustered by `order_date` to improve scan performance for date-range queries.

### Summary of Denormalization Strategy
This design transforms the source OLTP schema into a **Hybrid Star Schema** where:
1.  **Fact Tables** (`s_orders`, `s_sale_lineitem`, `s_sales`, `s_returns`, `s_inventory_snapshots`) are heavily denormalized to include all necessary dimension attributes directly in the fact table. This eliminates the need for `JOIN` operations during analytical queries.
2.  **Dimension Tables** (`s_store_dim`, `s_item_dim`, etc.) are provided for logical clarity and potential use in `LEFT JOIN` scenarios if specific detail is required, but the primary read path is the denormalized fact table.
3.  **Unified Channels**: Catalog and Web orders are merged into `s_orders`, and their line items into `s_order_lineitem`, enabling cross-channel analysis.
4.  **Time-Series Support**: Inventory is modeled as snapshots, and all facts include normalized `DATE` columns,
