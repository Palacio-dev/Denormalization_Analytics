# Phase 1 – Schema Assessment

### Entity Relationships & Cardinalities
*   **Users**: Represents the primary consumer entity. Cardinality is "Many" regarding `user_entitlements`.
*   **Entitlements**: Represents the product/feature catalog. Cardinality is "One" regarding `user_entitlements` (in terms of definition), but "Many" regarding usage (`useCount` aggregates over time).
*   **User_Entitlements**: This is a **Fact Table** (specifically a sparse transactional fact) linking Users to Entitlements. It acts as the bridge.
*   **Relationships**: One-to-Many from `users` to `user_entitlements`. One-to-Many from `entitlements` to `user_entitlements`.

### Join Paths & Access Patterns
In an OLTP environment, joins are frequent but small in scope. In an OLAP environment:
1.  **Aggregation by User**: Summing `useCount` per `user_id` over a date range.
2.  **Aggregation by Feature**: Summing `useCount` per `featureType` and `packageType`.
3.  **Status Filtering**: Filtering active users (`activeFlag = 1`) who have used a specific entitlement.
4.  **Time-Series Analysis**: Tracking `useCount` trends against `activeDate`/`inactiveDate`.

Currently, the `user_entitlements` table forces a Join between `users` and `entitlements` for almost every analytical query. Given that `users` and `entitlements` are likely small to medium-sized reference tables, the overhead of joining them repeatedly in complex aggregations is significant.

### Fact/Dimension Identification
*   **Dimensions**: `users` (User attributes), `entitlements` (Feature/Product attributes).
*   **Fact**: `user_entitlements` (The link/transaction). Note: `useCount` is currently stored in the dimension table, which is an anomaly for dimensional modeling. `useCount` should ideally be in a dedicated usage fact table, but for this specific schema transformation, we will treat `user_entitlements` as the primary fact table containing the consumption metrics.

# Phase 2 - Analytical Modeling Strategy

### Chosen Architecture: **Star Schema with Wide Denormalization**
We will adopt a **Star Schema** architecture where the central fact table (`user_entitlements`) is "widened" to include the key attributes of both dimensions (`users` and `entitlements`).

**Justification:**
1.  **Query Simplicity**: Reporting queries typically aggregate by `user_id`, `featureType`, or `packageType`. Joining three tables (`users` + `entitlements` + `user_entitlements`) adds latency, especially with complex `GROUP BY` clauses.
2.  **Filter Pushdown**: Filters on `activeFlag`, `featureType`, or `packageType` can be pushed down to the storage engine without needing to match keys first.
3.  **BI Compatibility**: BI tools (Tableau, PowerBI, Looker) excel at scanning star schemas. They often struggle with deep joins and performant aggregations on large fact tables unless indexed heavily.
4.  **Traceability**: While we denormalize, we retain `user_id` and `entitlement_id` as foreign keys to maintain a logical link back to the source entities for auditability.

### Denormalization Decisions & Tradeoffs

| Decision ID | Description | Performance Objective | Join Reduction | Data Redundancy | Update Implications |
| :--- | :--- | :--- | :--- :--- | :--- |
| **D1** | **Absorb User Attributes**: Move `users.id` (already present) and potentially user metadata (if added) into `user_entitlements`. | Eliminates the need to join `users` for 90% of queries. | -2 Joins (User + Entitlement) | Low (Only `id` repeated if `users` is tiny; otherwise negligible). | Requires updating `user_entitlements` whenever a user record changes. |
| **D2** | **Absorb Entitlement Attributes**: Move `featureType`, `packageType`, `activeFlag`, `useLimit` into `user_entitlements`. | Enables filtering and grouping by feature/package without joining `entitlements`. | -2 Joins (Total 0 joins needed for attribute access). | Medium (Entitlements table may have 10k+ rows; `user_entitlements` has millions). | **High Risk**: Changing an entitlement's `featureType` requires updating every row in `user_entitlements` that references it. |
| **D3** | **Promote `useCount` to Fact**: Treat `useCount` as the primary fact metric in `user_entitlements`. | Supports direct aggregation (`SUM(useCount)`). | N/A | N/A | `useCount` is likely an aggregate itself. If the source updates daily, we must ensure the `user_entitlements` table reflects the latest state or use a dedicated usage fact table. For this exercise, we assume `user_entitlements` holds the snapshot. |

# Phase 3 – Analytical Physical Model Design

### Table Definitions

#### 1. Fact Table: `fact_user_entitlement_usage`
This table replaces `user_entitlements` and acts as the central hub. It absorbs dimensions to minimize joins.

```sql
CREATE TABLE fact_user_entitlement_usage (
    -- Surrogate Key / Primary Key
    usage_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    
    -- Dimension Keys (Retained for traceability)
    user_id INT NOT NULL,
    entitlement_id INT NOT NULL,
    
    -- Absorbed Attributes from 'users' dimension
    -- (Assuming 'users' table only has 'id', we keep it as the key, 
    -- but in a real scenario, we'd absorb user_name, email, etc. here)
    
    -- Absorbed Attributes from 'entitlements' dimension
    feature_type VARCHAR(4) NOT NULL,
    package_type VARCHAR(4) NOT NULL,
    use_limit INT NOT NULL,
    active_flag INT NOT NULL,
    
    -- Fact Attributes (Consumption Metrics)
    use_count INT NOT NULL DEFAULT 0,
    
    -- Derived/Calculated Attributes (Optional but recommended for speed)
    is_active_user BOOLEAN GENERATED ALWAYS AS (active_flag = 1),
    
    -- Partitioning: Partition by Date Range or User ID for efficient scanning
    -- Strategy: Partition by 'entitlement_id' or 'user_id' depending on query load
    -- Assuming high cardinality on user_id, partitioning by entitlement_id might be better for feature reporting
    -- However, for time-series usage, we usually partition by date. Since no date exists here,
    -- we will partition by 'entitlement_id' to optimize feature-based aggregation.
    PARTITION BY LIST (entitlement_id)
    
    -- Clustering: Cluster by the most selective column for filtering
    -- 'user_id' is likely the most selective filter in user reporting
    CLUSTER BY user_id
);
```

*Note: In a production environment, `useCount` is often a running total. If the source `user_entitlements` represents a point-in-time snapshot, we should consider a dedicated `fact_usage_events` table. However, adhering strictly to the provided schema transformation, we treat `useCount` as the fact value.*

#### 2. Dimension Table: `dim_entitlements` (Simplified)
Since we absorbed attributes, we can keep the `entitlements` table as a lightweight reference or remove it if `featureType` and `packageType` are atomic. To preserve traceability and allow updates to the catalog without locking the fact table (if possible via ETL), we keep it but note that the fact table is the source of truth for reporting.

*Decision: We will keep `entitlements` as a reference table but acknowledge that the Fact table holds the denormalized data.*

*Correction for the "Wide Denormalized" approach requested:*
To strictly follow the **Wide Denormalized** strategy for maximum performance on this specific schema, the `entitlements` and `users` tables might be effectively "flattened" into the fact table for read operations. However, to maintain data integrity and allow updates to the master data without rewriting the entire fact table (which is expensive), we keep the reference tables but ensure the Fact table is the one queried.

**Refined Fact Table Strategy (Final):**
We will create a single, massive fact table that contains all columns from `users`, `entitlements`, and `user_entitlements` (minus the PKs which are redundant).

```sql
-- Final Denormalized Fact Table
CREATE TABLE fact_analytics_entitlements (
    -- Surrogate Key
    entity_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    
    -- Core Relationship Keys
    user_id INT NOT NULL,
    entitlement_id INT NOT NULL,
    
    -- Absorbed Dimensions (No Joins Required)
    feature_type VARCHAR(4) NOT NULL,
    package_type VARCHAR(4) NOT NULL,
    use_limit INT NOT NULL,
    active_flag INT NOT NULL,
    
    -- Fact Metrics
    use_count INT NOT NULL DEFAULT 0,
    
    -- Computed Columns for faster filtering
    is_active BOOLEAN GENERATED ALWAYS AS (active_flag = 1),
    
    -- Partitioning: Partition by User ID for user-centric reporting
    -- Clustering: Cluster by Feature Type for feature-centric reporting
    PARTITION BY user_id
    CLUSTER BY feature_type
);
```

**Why this design?**
1.  **Zero Joins**: Queries can now filter `WHERE feature_type = 'X'` or `GROUP BY user_id` without touching `dim_users` or `dim_entitlements`.
2.  **Scalability**: `user_id` partitioning allows parallel scanning for user reports. `feature_type` clustering allows parallel scanning for product reports.
3.  **Tradeoff**: If `entitlements` has 100,000 rows and `users` has 10,000 rows, and `user_entitlements` has 50 million rows, the redundancy factor is roughly 50x (one row in fact per link). This is acceptable because the alternative (joining) would be orders of magnitude slower for aggregations.
