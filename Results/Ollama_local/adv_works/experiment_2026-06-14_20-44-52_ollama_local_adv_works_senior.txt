**Entity Relationships & Cardinalities:**

**Join Paths:**

4.  **KPIs:** Average order value, sales per employee, inventory turnover.

### Phase 2 - Analytical Modeling Strategy

**Chosen Architecture:** **Hybrid Star Schema with Reference Data Absorption**

**Justification:**
While a pure Star Schema is ideal, the Adventure Works schema contains deep hierarchies (Country $\to$ State $\to$ City) and many-to-many relationships (Employee $\leftrightarrow$ Department, Employee $\leftrightarrow$ Territory).
*   **Reference Data Absorption:** Instead of joining `SalesTerritory` to `CountryRegion` and `StateProvince` via multiple joins, we absorb these attributes directly into the `SalesTerritory` fact table. This eliminates the need for lookup joins for geography.
*   **Dimension Flattening:** We flatten `Product` by absorbing `ProductCategory`, `ProductSubcategory`, `Class`, `Style`, and `Size` directly into the `Product` table.
*   **Fact Splitting (Optional but recommended for specific patterns):** For highly granular time-series analysis, `SalesOrderDetail` might be split, but for this dataset, keeping it as a single fact table with absorbed dimensions is sufficient and maintains referential integrity for line-item tracking.
*   **Surrogate Keys:** We utilize surrogate keys (`int`) for all dimensions to ensure stable references across data marts and to avoid type mismatches during joins.

**Tradeoffs:**
*   **Storage Growth:** We introduce significant data redundancy. For example, `ProductCategory.Name` is stored in both `Product` and `ProductCategory` (which we drop).
*   **Update Complexity:** Updating a country's name requires updating the `SalesTerritory` table (and potentially `SalesOrderDetail` if we had historical orders referencing the old name, though we usually update the dimension).
*   **Maintenance:** The source system (`AdventureWorks`) has a normalized structure. This transformation requires an ETL process to populate the denormalized columns from the source tables.

### Phase 3 – Analytical Physical Model Design

**Design Principles:**
1.  **Wide Fact Tables:** `SalesOrderHeader` and `SalesOrderDetail` will be "wide" tables containing all dimension attributes relevant to reporting.
2.  **Single Source of Truth:** The `Product` table will be the canonical source for product attributes.
3.  **Date Handling:** A dedicated `Date` dimension table is created to standardize date comparisons and enable efficient time-based filtering.
4.  **Partitioning:** Fact tables will be partitioned by `orderdate` (or `transactiondate`) to facilitate pruning in large datasets.
5.  **Clustering:** Data will be clustered by the primary business key (`salesorderid`, `purchaseorderid`, etc.) to improve join performance for OLAP engines.
