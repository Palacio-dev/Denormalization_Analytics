# Phase 1 – Schema Assessment

### Entity Relationships and Cardinalities
The source schema represents a classic hierarchical structure:
1.  **UF (State)**: Root of the hierarchy. One-to-Many relationship with `MUNICIPIO`.
2.  **MUNICIPIO (Municipality)**: Intermediate dimension. One-to-Many with `IES` and `ESCOLA`. Contains aggregated metrics (`media_ideb`, `qtd_habitantes`, etc.) that are likely static or slowly changing.
3.  **IES (Institution)**: Many-to-Many with `ESCOLA` (via `REDE` or specific attributes, though the schema shows `IES` has a `REDE` and `ESCOLA` has a `REDE`, suggesting a potential many-to-many or a normalization artifact where schools belong to institutions and networks). *Correction*: Looking closely, `IES` has `sigla_ies` and `REDE`, while `ESCOLA` has `cod_escola` and `REDE`. The link between them is missing in the source DDL, implying a many-to-many or a missing join table. For analytics, we will treat `IES` and `ESCOLA` as sibling dimensions under `MUNICIPIO` or link them via a common `REDE` dimension if distinct. However, to minimize joins, we will absorb `IES` and `ESCOLA` attributes into `MUNICIPIO` if they are stable, or keep them as leaf dimensions with full attribute expansion.
    *   *Assumption*: `IES` and `ESCOLA` are leaf dimensions. `MUNICIPIO` aggregates data from them.
4.  **ANNO (Year/Event)**: This is the critical fact table. It acts as the "Time/Event" dimension. It links `CURSO`, `ENADE`, `SAEB`, `IDEB`, and `ANO`.
    *   Note: The source schema has `ANNO` referencing `CURSO`, `ENADE`, `SAEB`, `IDEB`, and `ANO` (self-reference?). This suggests a many-to-many relationship where a specific course can have multiple years of ENADE/SAEB/IDEB data.
    *   `CURSO` links to `IES`.

### Query Access Patterns
Analytical workloads on this domain typically involve:
1.  **Hierarchical Aggregations**: Sum of students, average IEB/ENADE scores grouped by State -> Municipality -> Institution -> School.
2.  **Time-Series Analysis**: Trends over years (`ANO`) for specific courses or institutions.
3.  **Complex Joins**: Users often need to join `MUNICIPIO` (metrics) with `IES` (details) and `ANNO` (events) to get a snapshot of performance.
4.  **Filtering**: "Show all municipalities in UF 'SP' with IEB > 5.0".

### Identified Issues in Source
*   **Fragmented Dimensions**: `UF`, `MUNICIPIO`, `IES`, `ESCOLA` are split.
*   **Sparse Fact Table**: `ANNO` is a sparse fact table with multiple foreign keys, creating a massive number of rows if every combination exists.
*   **Join Explosion**: A query like "Total ENADE students per UF" requires joining `UF` -> `MUNICIPIO` -> `IES` -> `CURSO` -> `ANNO` -> `ENADE`. This is a 5-way join, which is inefficient for BI tools.

# Phase 2 - Analytical Modeling Strategy

### Chosen Architecture: **Star Schema with Wide Dimension Flattening**

**Justification:**
The goal is to maximize query speed for BI platforms (Tableau, PowerBI, Looker) and OLAP engines (Snowflake, BigQuery, Redshift).
1.  **Denormalization of Dimensions**: We will flatten `IES` and `ESCOLA` attributes into the `MUNICIPIO` dimension where possible (e.g., total institutions, total schools, network types) to eliminate joins between leaf dimensions.
2.  **Absorption of Sparse Facts**: Since `ANNO` links multiple metrics (`ENADE`, `SAEB`, `IDEB`, `CURSO`), we will create a **Wide Fact Table** (`FATO_METRICAS`) that holds the aggregated data directly, rather than relying on a sparse many-to-many join table.
3.  **Reference Data Absorption**: `UF` will be fully absorbed into `MUNICIPIO` to allow direct querying of state-level metrics without joining.

**Performance Objectives & Trade-offs:**

| Decision | Performance Objective | Join Reduction | Data Redundancy | Maintenance Implication |
| :--- | :--- | :--- | :--- :--- |
| **Absorb UF into MUNICIPIO** | Eliminates the first join in any state-level query. | -1 Join | Stores `sigla_uf` and `nome_uf` in every municipality row. | Low impact (UF data is static). |
| **Flatten IES/ESCOLA into MUNICIPIO** | Reduces complexity from 4+ joins to 1-2 joins. | -3 Joins | Stores counts and network types for every municipality. | Requires accurate counts per municipality (aggregation job). |
| **Create Wide Fact Table** | Enables direct slicing by Year/Course without joining sparse tables. | -4 Joins | Stores raw metrics for every Course-Year combination. | Requires nightly aggregation jobs to populate the wide table. |

# Phase 3 – Analytical Physical Model Design

### Design Principles
1.  **Granularity**: The fact table will be at the level of `Curso` x `Ano` x `Metrica`.
2.  **Partitioning**: The `FATO_METRICAS` table will be partitioned by `ANO` to optimize pruning.
3.  **Clustering**: The `DIMENSAO_MUNICIPIO` table will be clustered on `(ID_MUNICIPIO, SIGLA_UF)` for fast hierarchical lookups.
4.  **Surrogate Keys**: All dimensions use auto-incrementing surrogate keys (`ID_`) to ensure stable references.

### Table Definitions

#### 1. Dimension: Municipality (Flattened)
Combines `UF`, `MUNICIPIO`, `IES`, and `ESCOLA` attributes to create a comprehensive dimension.

```sql
CREATE TABLE DIMENSAO_MUNICIPIO (
    id_municipio INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id_uf INT NOT NULL,
    sigla_uf VARCHAR(2) NOT NULL,
    nome_uf VARCHAR(100) NOT NULL,
    nome_municipio VARCHAR(100) NOT NULL,
    
    -- Aggregated attributes from IES and ESCOLA
    qtd_ies_total INT NOT NULL,
    qtd_escolas_total INT NOT NULL,
    rede_maioria VARCHAR(100), -- Simplified for analytics
    
    -- Metrics (Assuming these are aggregated or stored here for speed)
    media_ideb REAL,
    media_saeb REAL,
    media_enade REAL,
    total_participantes INT,
    
    -- Indexing
    CONSTRAINT fk_dim_uf FOREIGN KEY (id_uf) REFERENCES DIMENSAO_UF (id_uf)
);
```

#### 2. Dimension: UF (Reference Absorbed)
Since `UF` is fully absorbed, we can keep a minimal reference table or merge it. For traceability, we keep a minimal `DIMENSAO_UF` but ensure `DIMENSAO_MUNICIPIO` references it.

```sql
CREATE TABLE DIMENSAO_UF (
    id_uf INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sigla_uf VARCHAR(2) NOT NULL,
    nome_uf VARCHAR(100) NOT NULL,
    qtd_habitantes INT NOT NULL
);
```

#### 3. Fact Table: Wide Metrics (Denormalized)
This table replaces the complex `ANNO` join structure. It holds the calculated metrics directly.

```sql
CREATE TABLE FATO_METRICAS (
    id_fato INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    id_municipio INT NOT NULL,
    id_curso INT NOT NULL,
    id_ano INT NOT NULL,
    
    -- Metrics from ENADE
    total_inscritos_enade INT,
    total_concluintes_enade INT,
    nota_bruta_ce_enade REAL,
    nota_padronizada_ce_enade REAL,
    nota_bruta_fg_enade REAL,
    nota_padronizada_fg_enade REAL,
    
    -- Metrics from SAEB
    nota_mat_saeb REAL,
    nota_port_saeb REAL,
    nota_padrao_saeb REAL,
    
    -- Metrics from IDEB
    nota_ideb_real REAL,
    ind_rend_ideb REAL,
    
    -- Computed metrics (e.g., participation rate)
    taxa_participacao REAL,
    
    -- Partitioning Key
    CONSTRAINT fk_fact_muni FOREIGN KEY (id_municipio) REFERENCES DIMENSAO_MUNICIPIO (id_municipio),
    CONSTRAINT fk_fact_curso FOREIGN KEY (id_curso) REFERENCES DIMENSAO_CURSO (id_curso),
    CONSTRAINT fk_fact_ano FOREIGN KEY (id_ano) REFERENCES DIMENSAO_ANO (id_ano)
);
```
