### Analysis and Denormalization Strategy

#### Section 1: Structural Analysis and Decisions

**Summary:**
The original schema follows a strict Third Normal Form (3NF) design, separating entities like `aircrafts`, `airports`, `bookings`, 
`flights`, `tickets`, `seats`, `ticket_flights`, and `boarding_passes`. While efficient for data integrity and point lookups, 
this structure suffers from high join counts during complex analytical reporting (e.g., "Total revenue by city for flights using 
Boeing 737 in the last 6 months").

The denormalization strategy focuses on creating a **Star Schema** or **Data Warehouse** style layout. The goal is to create a
 central "Fact" table that aggregates transactional details with denormalized dimension attributes to eliminate joins.

**Structural Decisions:**
1.  **Merge `tickets` and `ticket_flights` into `fact_bookings`**: These tables share a primary key (`ticket_no`) and have overlapping attributes (`book_ref`, `passenger` details, `flight_id`, `amount`, `fare_conditions`). Merging them creates a single atomic fact record.
2.  **Merge `boarding_passes` into `fact_bookings`**: Boarding passes are tightly coupled with tickets and flights. Adding `boarding_no` and `seat_no` to the fact table allows reporting on seat utilization without joining a separate dimension table.
3.  **Create `dim_flight_details`**: Instead of joining `flights` with `aircrafts` and `airports` on every query, we create a derived table containing flight metadata, airport names, aircraft models, and status. This pre-calculates the join path.
4.  **Create `dim_passenger_bookings`**: Merges `bookings` and `tickets` to store booking reference, date, amount, and passenger details in one place.

**Attribute-Level Changes:**
1.  **Computed Attributes**: Added `city`, `airport_name`, `aircraft_model`, and `status` directly to the `dim_flight_details` table (previously in separate tables).
2.  **Derived Keys**: Added `passenger_name` and `contact_data` directly to the `dim_passenger_bookings` table (previously split between `bookings` and `tickets`).
3.  **Removed Redundancy**: Removed `flight_id` from `dim_passenger_bookings` as it is implied by the booking reference in this specific denormalized context, or kept if multi-segment tickets are common (kept for safety).

**Tradeoffs:**
1.  **Write Performance vs. Read Performance**: The new schema requires significantly more `INSERT` operations (one row per ticket/booking instead of two). However, `SELECT` performance will improve drastically for analytical queries.
2.  **Data Freshness**: If the underlying transactional system changes frequently, the denormalized tables must be refreshed (ETL process) to ensure accuracy.
3.  **Storage Overhead**: Storing repeated strings (e.g., airport names) increases storage size but reduces CPU usage during joins.

#### Section 2: Query Patterns

**Query Pattern 1: Complex Flight Analysis**
*   **Pattern**: "Calculate total revenue per city for flights operated by specific aircraft models, including actual departure times."
*   **Original Challenge**: Requires `JOIN`s between `bookings`, `ticket_flights`, `flights`, `aircrafts_data`, and `airports_data`.
*   **Denormalized Benefit**: A single `JOIN` (or even no join if pre-aggregated) against `dim_flight_details` and `dim_passenger_bookings`.

**Query Pattern 2: Passenger Seat Utilization**
*   **Pattern**: "List all passengers booked for Seat 10A across all flights in the last month."
*   **Original Challenge**: Requires joining `tickets`, `boarding_passes`, `flights`, and `seats`.
*   **Denormalized Benefit**: Direct lookup in the merged `fact_bookings` table which now contains `seat_no` and `passenger_name`.
