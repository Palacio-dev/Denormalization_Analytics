Based on the RISEN Framework, here is the analysis and design for denormalizing the Adventure Works Cycles schema into a 
single Big Table model.

### Section 1: Analysis and Strategy

**Summary**
The denormalization strategy follows the **ONE-BIG-TABLE MODEL**. The goal is to consolidate the entire Adventure Works Cycles
relational schema (approx. 40+ tables) into a single, massive table. This eliminates join operations, significantly reducing 
query latency for analytical workloads that aggregate data across departments, products, sales, and manufacturing. The strategy 
prioritizes read performance over write complexity, accepting that the table will be wide.

**Structural Decisions**
1.  **Single Table Creation**: A new table named `adventure_works_flat` is created.
2.  **Primary Key Selection**: `businessentityid` is selected as the primary key because it is the root identifier connecting almost 
all tables (Person, Employee, Customer, Vendor, Product, etc.). Tables without this ID (e.g., `Department`, `Shift`, `ProductCategory`)
will use a composite key or a surrogate ID mapped to the main key.
3.  **Attribute Merging**:
    *   **Shared Attributes**: Attributes like `modifieddate`, `rowguid`, and common columns (e.g., `name`, `date`) are duplicated 
    for every table to ensure data availability in a single row context.
    *   **Naming Convention**: To avoid ambiguity when multiple tables share column names (e.g., `name` in `Department`, `Employee`, 
    `Product`, `SalesTerritory`), the source table name is prefixed to the column name (e.g., `dept_name`, `emp_name`, `prod_name`).
    *   **Foreign Key Removal**: All `REFERENCES` constraints are removed. Instead, the child table's ID is stored as a column in 
    the parent table's row (e.g., `dept_id` is a column in the `EmployeeDepartmentHistory` row).
4.  **Data Type Preservation**: All original data types (e.g., `numeric(8,2)`, `xml`, `bytea`, `uuid`) are preserved exactly.

**Attribute-Level Changes**
1.  **Prefixing**: Columns with identical names across different tables are renamed with a prefix (e.g., `emp_birthdate` vs 
`prod_listprice`).
2.  **Surrogate Keys**: Tables like `Department` (no business entity link) and `ProductCategory` (no direct business entity link) 
use `departmentid` and `productcategoryid` respectively as their own local keys within the flat table, or are joined via the 
`employeedepartmenthistory` table's structure.
3.  **XML/Bytea Handling**: Large BLOBs (`bytea`) and XMLs (`xml`) are preserved as-is to maintain data integrity, though they will
 increase row size.

**Tradeoffs**
1.  **Write Performance**: Inserting a row for every entity (Employee, Product, SalesOrder, etc.) will be slow due to the massive 
number of columns.
2.  **Storage Overhead**: The table will be significantly wider than the normalized version, consuming more disk space and 
potentially causing index bloat if indexes are created on the flat table.
3.  **Reconstruction**: While all data is present, reconstructing the original relational relationships requires filtering and grouping, which is the point of denormalization (analytical queries are faster, but the "flat" nature hides relationships visually).

### Section 2: Query Patterns

**Inferred Query Patterns**
1.  **Sales Performance by Region**: "Show total sales, costs, and salesperson bonuses grouped by Territory and SalesTerritory."
    *   *Motivation*: Requires joining `SalesOrderHeader`, `SalesTerritory`, `SalesPerson`, and `SalesTerritoryHistory`. In the flat table, this is a simple `GROUP BY`.
2.  **Employee Details with Payroll**: "Get all active employees, their department, shift, and current pay rate."
    *   *Motivation*: Requires joining `Employee`, `EmployeeDepartmentHistory`, `Department`, `Shift`, and `EmployeePayHistory`.
3.  **Product Cost Analysis**: "Calculate the standard cost of all products, including their BOM components and manufacturing locations."
    *   *Motivation*: Requires traversing `Product`, `BillOfMaterials`, `ProductInventory`, `Location`, and `WorkOrder`.
