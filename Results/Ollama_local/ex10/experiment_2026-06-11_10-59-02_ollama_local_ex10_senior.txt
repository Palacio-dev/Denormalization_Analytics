**Join Paths:**

### Phase 2 - Analytical Modeling Strategy

**Chosen Architecture: Star Schema with Reference Data Absorption**

**Justification:**
For analytical workloads, the **Star Schema** is superior to Snowflake because it reduces join depth from $N$ to 1 (Fact + Dimensions). By absorbing dimension attributes directly into the Fact tables (Wide Denormalization), we eliminate the need to join back to dimension tables for simple attribute retrieval.
*   **Reference Data Absorption:** Instead of joining `paises` for `nome`, `fundacao`, or `continente`, we store these columns directly in the fact tables.
*   **Dimension Flattening:** `continente` is absorbed into `paises`. `fonte_energia` is absorbed into `consumo_anual`.

**Performance Objectives & Tradeoffs:**
*   **Join Reduction:** We reduce the maximum join depth from 3+ to 1. This significantly lowers CPU usage during aggregation.
*   **Data Redundancy:** We introduce redundancy by duplicating country names, continents, and energy names in multiple fact tables.
    *   *Quantification:* If we have 100 countries, 50 years, and 10 energy types, we are duplicating dimension data roughly 50x (Fact1) + 50x (Fact2) + ...
*   **Maintenance Implications:**
    *   *Risk:* Updating a country name requires updating multiple fact tables.
    *   *Mitigation:* Since this is an analytics warehouse, we assume dimension updates are rare (e.g., country renaming). If critical, we can implement a "Golden Record" table with a trigger, but for pure analytical speed, redundancy is acceptable.
    *   *Storage:* Expect a 30-40% increase in storage due to repeated string data, which is negligible compared to the gains in query speed.

### Phase 3 – Analytical Physical Model Design

The new schema consists of three main Fact tables and one small Dimension table (kept for auditability or if strict referential integrity is needed, though we will absorb data into facts).

**Key Design Decisions:**
1.  **Surrogate Keys:** `id_consumo`, `id_emissao`, `id_pop` remain as surrogate keys for the fact tables.
2.  **Date Handling:** `ano` is kept as an integer for speed, but in production, a `date` type with partitioning by year would be recommended. Here, we optimize for the existing integer constraint.
3.  **Clustering:** Tables should be clustered/partitioned by `ano` (Year) to allow efficient pruning of data for specific years.
4.  **Data Types:** Changed `porcentagem` to `numeric` or `decimal` if precision is needed, but keeping `integer` for speed if it represents whole percentages. `quantidade_emitida` and `quantidade_hab` are `bigint` for large numbers.
