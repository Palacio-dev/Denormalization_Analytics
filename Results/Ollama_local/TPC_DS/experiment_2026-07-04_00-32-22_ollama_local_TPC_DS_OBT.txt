### Section 1: Analysis and Strategy

**Summary:**
The denormalization strategy adopts the **One-Big-Table Model** to optimize read performance for complex analytical queries involving orders, line items, inventory, and returns. By eliminating foreign keys and joining relationships, the schema reduces I/O overhead during query execution, as the database engine no longer needs to resolve relationships across multiple tables. Instead, the single table acts as a wide dataset where related entities (Purchase, Catalog Order, Web Order, Line Items, Returns, Inventory) are stored as distinct rows sharing a common composite or hierarchical key structure.

**Structural Decisions:**
*   **D1 - Single Entity Table Creation:** All original tables (`s_purchase_lineitem`, `s_purchase`, `s_catalog_order`, `s_web_order`, `s_catalog_order_lineitem`, `s_web_order_lineitem`, `s_store_returns`, `s_catalog_returns`, `s_inventory`) are merged into a single table named `s_data_master`.
*   **D2 - Composite Primary Keys:** Since the original schema relies on specific business keys (e.g., `purc_purchase_id` for purchases, `cord_order_id` for catalog orders), the new table uses a `row_id` (integer) as the single global primary key. To ensure unique identification of each row's context, a `source_type` (varchar) is added to categorize the record (e.g., 'PURCHASE', 'CATALOG_ORDER', 'INVENTORY'), and the specific business key is stored as a separate column (e.g., `purc_purchase_id`, `cord_order_id`).
*   **D3 - Attribute Flattening:** All columns from the 9 source tables are moved to the new table. Columns that were foreign keys in the original schema (like `cord_bill_customer_id` or `sret_purchase_id`) are now treated as regular attributes.

**Attribute-Level Changes:**
*   **A1 - Prefixing for Ambiguity:** In the original schema, `item_id` and `quantity` exist in multiple tables (Purchase Line, Catalog Order Line, Web Order Line, Returns). While the original schema distinguished them by table context, the denormalized model flattens this. To maintain semantic clarity within the single table, columns are prefixed with their original table entity name (e.g., `purc_item_id`, `cord_item_id`, `inv_item_id`).
*   **A2 - Data Type Preservation:** All original data types (`integer`, `numeric(7,2)`, `char(16)`, `varchar(100)`) are strictly preserved to ensure data integrity and compatibility with existing applications that expect these specific formats.

**Tradeoffs:**
*   **T1 - Write Performance vs. Read Performance:** This approach significantly improves **Read Performance** (fewer joins) but may degrade **Write Performance** slightly due to the larger row size and the lack of indexed foreign key relationships for referential integrity enforcement. Data integrity must be managed via application logic or triggers rather than database constraints.
*   **T2 - Storage Overhead:** The single table approach increases storage overhead due to repeated storage of common attributes (like `item_id` or `date`) across different record types, which is a necessary trade-off for the "One-Big-Table" analytical model.
