### Phase 1 – Schema Assessment

**Entity Relationships & Cardinalities:**
The source schema represents the classic TPC-H benchmark, characterized by a 1-to-many relationship between entities (e.g., one Nation has many Suppliers; one Supplier supplies many Parts). The `ORDERS` and `LINEITEM` tables act as the primary transactional facts, linking customers, suppliers, and parts through intermediate keys.

**Join Paths:**
Analytical queries on this schema typically involve deep join chains:
`LINEITEM` → `ORDERS` → `CUSTOMER` → `NATION` → `REGION`
`LINEITEM` → `PART`
`LINEITEM` → `SUPPLIER` → `NATION` → `REGION`

**Query Access Patterns:**
Reporting environments for this schema focus on:
1.  **Aggregations:** Summing quantities, revenues, or counts grouped by geography (Region/Nation) or product attributes (Type/Brand).
2.  **Filtering:** Filtering by date ranges, product categories, or customer segments.
3.  **Cross-joins:** Combining sales data with static reference data (Nation, Region, Part attributes).

**Fact vs. Dimension Analysis:**
*   **Fact Tables:** `ORDERS` (Order facts) and `LINEITEM` (Transaction facts).
*   **Dimension Tables:** `CUSTOMER`, `SUPPLIER`, `NATION`, `REGION`, `PART`.
*   **Granularity:** `LINEITEM` is the finest granularity (individual line items), making it the anchor for most analytical queries.

### Phase 2 - Analytical Modeling Strategy

**Chosen Architecture: Hybrid Dimensional Model (Star Schema with Reference Data Absorption)**

**Justification:**
While a pure Star Schema is ideal for BI tools, the TPC-H schema involves complex multi-level hierarchies (Region -> Nation -> Customer/Supplier) and specific attribute dependencies (e.g., Part Type determines Container). A pure Snowflake schema (keeping all relationships normalized) results in too many joins for analytical engines, leading to scan times that exceed query timeout limits.
A **Hybrid Star Schema** approach is selected because:
1.  It places `LINEITEM` and `ORDERS` as the central fact tables.
2.  It absorbs critical dimension attributes directly into the fact tables (e.g., `PART_TYPE`, `NATION_NAME`) to eliminate joins for the most common query patterns.
3.  It maintains a dedicated "Reference" table only for highly granular, frequently changing attributes where redundancy is too high (e.g., full `ADDRESS` strings if queried per customer, though often aggregated by Region).

**Denormalization Decisions & Tradeoffs:**

| Decision ID | Description | Performance Objective | Expected Join Reduction | Data Redundancy | Update Implications |
| :--- | :--- | :--- | :--- :--- | :--- |
| **D1** | **Absorb Part Dimensions into LINEITEM:** Move `P_TYPE`, `P_CONTAINER`, `P_BRAND`, `P_RETAILPRICE` from `PART` to `LINEITEM`. | Eliminate join between `LINEITEM` and `PART`. Enables immediate filtering and grouping by product attributes. | Reduces `LINEITEM` -> `PART` joins from 1 to 0. | `LINEITEM` grows significantly (approx. 4-5 extra columns per row). | Requires updating `LINEITEM` on Part changes. Mitigated by infrequent Part updates in OLTP vs. massive Lineitem volume. |
| **D2** | **Absorb Order Dimensions into ORDERS:** Move `O_ORDERSTATUS`, `O_ORDERPRIORITY`, `O_CLERK` (if needed for reporting) and potentially `O_TOTALPRICE` logic into `LINEITEM` if revenue calc is frequent. | Simplify `ORDERS` -> `LINEITEM` join. Allow direct revenue calculation in `LINEITEM` if tax/discount is pre-calculated (or keep in Orders for audit). *Decision: Keep `ORDERS` normalized for audit, but absorb `O_TOTALPRICE` into `LINEITEM` if derived, otherwise keep in `ORDERS`.* <br>*Correction:* Best practice: Keep `ORDERS` normalized for status/priority, but absorb `O_CUSTKEY` logic into `CUSTOMER` facts. | Reduces `LINEITEM` -> `ORDERS` join complexity for status/priority reporting. | Minimal redundancy; `ORDERS` remains a key reference. | Standard OLTP update patterns apply. |
| **D3** | **Absorb Geography into LINEITEM:** Create columns `L_NATION_NAME`, `L_REGION_NAME` in `LINEITEM`. | Eliminate 2-level join chain (`LINEITEM` -> `ORDERS` -> `CUSTOMER` -> `NATION` -> `REGION`). Enables instant geographic aggregation. | Reduces `LINEITEM` -> `CUSTOMER` -> `NATION` -> `REGION` path to a single table scan. | High redundancy: Every line item repeats the Nation/Region name. | Nation/Region changes are rare (static reference data). High read volume justifies write cost. |
| **D4** | **Absorb Customer/Supplier Facts:** Add `C_MKTSEGMENT`, `S_ACCTBAL` to `LINEITEM` and `ORDERS` respectively. | Allow direct filtering by market segment or account balance without joining `CUSTOMER`/`SUPPLIER`. | Reduces `LINEITEM` -> `CUSTOMER` and `ORDERS` -> `SUPPLIER` joins. | Moderate redundancy. | Customer/Supplier data updates are frequent in OLTP. **Risk:** Data staleness in fact tables. **Mitigation:** Use ETL to refresh fact tables nightly; rely on denormalized data for historical reports, not real-time transactions. |

);
