# Principal Data Architect Analysis: Employee Analytics Transformation

## Phase 1 – Schema Assessment

**Entity Relationships & Cardinalities:**
*   **Employees (`employee`):** One-to-Many with Departments (via `department_employee` and `department_manager`) and Many-to-One
 with Salary/Title.
*   **Departments (`department`):** One-to-Many with Employees and Managers.
*   **Temporal Nature:** The schema is heavily normalized around time (SISDI pattern: System, Instance, Status, Date, Instance). Every fact has `from_date` and `to_date`, implying a Slowly Changing Dimension Type 2 (SCD2) or historical snapshot requirement.
*   **Hierarchies:** Implicit manager hierarchies exist in `department_manager`, but the current schema stores flat relationships (`emp_id`, `dept_id`) rather than parent-child chains.
*   **Fact Tables:**
    *   `department_employee`: Employee tenure in a department.
    *   `department_manager`: Reporting structure.
    *   `salary`: Compensation history.
    *   `title`: Role history.

**Query Access Patterns (Inferred):**
1.  **Managerial Reporting:** "List all employees in Dept X with their current title and salary." (Requires 3-4 joins).
2.  **Compensation Analysis:** "Calculate average salary by department for employees active in Q1 2023." (Requires joining Employee, Dept, and Salary).
3.  **Historical Trends:** "Show salary progression for Employee Y over time." (Scanning `salary` table).
4.  **Headcount Planning:** "Count employees per department by gender and hire year." (Aggregations across multiple tables).

**Key Bottlenecks in OLTP Model:**
*   **Join Explosion:** Queries requiring cross-table analysis (e.g., Salary + Title + Dept) require joining 4-5 tables. In large datasets, this creates significant I/O overhead.
*   **Filter Pushdown Limitations:** Filtering on `department_name` requires a join to `department` first, then pushing down to `department_employee`.
*   **SCD2 Complexity:** Maintaining `to_date` logic in analytical queries is complex; denormalizing attributes into a single "current" view simplifies this for read-only reporting.

---

## Phase 2 - Analytical Modeling Strategy

**Chosen Architecture: Hybrid Dimensional Model (Star Schema with Reference Data Absorption)**

**Justification:**
*   **Workload Type:** The primary workload is ad-hoc analytical querying and dashboarding. Join-heavy queries are the performance bottleneck.
*   **Dimension Flattening:** We will absorb `department` attributes into the fact tables (`department_employee`, `department_manager`) to eliminate the need for joins. This is more effective than a Snowflake model for BI tools which struggle with deep join chains.
*   **Reference Data Absorption:** `employee` demographics (gender, hire_date) will be absorbed into the main fact table (or a dedicated employee dimension if cardinality is high, but given the request for denormalization, we will create a consolidated `employee` fact table).
*   **Wide Fact Tables:** We will create "Wide" fact tables that contain all descriptive attributes (Name, Dept Name, Gender, etc.) to maximize the ability to filter and aggregate without joining.

**Decision Analysis:**

| Decision ID | Description | Performance Objective | Join Reduction | Data Redundancy | Update Implications |
| :--- | :--- | :--- | :--- :--- | :--- |
| **D1** | **Create `employee_facts`**: Merge `employee`, `salary`, `title`, and absorbed `department` attributes into a 
single wide table. | Eliminate joins between Employee, Salary, and Title tables. Enables direct filtering on `first_name` 
while aggregating salary. | **Reduces:** 3-4 joins to **0** (for self-join scenarios). | **High:** Stores Name, Gender, Title, 
Dept Name, Salary in one row. | **Low Impact:** Employee attributes are rarely changed. If `title` changes, we insert a new row 
(SCD2 logic) rather than updating. |
| **D2** | **Create `department_facts`**: Merge `department` attributes directly into the `department_employee` and 
`department_manager` tables. | Eliminates the need to join `department` table for any department-level query. 
| **Reduces:** 1-2 joins to **0**. | **Medium:** Dept name is repeated per employee. | **Low Impact:** Dept structure rarely changes. |
| **D3** | **Absorb `employee` attributes**: Move `birth_date`, `gender`, `hire_date` from `employee` table to `employee_facts`. | Allows grouping by demographic attributes without joining the `employee` dimension. | **Reduces:** 1 join. | **Medium:** Birth date repeated. | **Low Impact:** Demographics are static. |

## Phase 3 – Analytical Physical Model Design

**Design Rationale:**
1.  **Granularity:** The primary granularity is the **Employee** (per time period or current state).
2.  **Partitioning:** We will partition by `hire_date` (for employee history) and `from_date` (for salary/title history) to enable efficient pruning of historical data in large datasets.
3.  **Clustering:** Cluster by `id` and `hire_date` to optimize range scans for "employees hired in 2020".
4.  **Traceability:** We include `employee_id` as a surrogate key in all tables to maintain logical traceability back to the original ID if needed, though the `id` itself serves as the primary key.

### Proposed Denormalized Schema (SQL DDL)

```sql
-- 1. Master Employee Fact Table (Wide)
-- Contains: Employee demographics, Current Dept info, Current Title, Current Salary
-- Note: For SCD2 support, we assume this table represents 'Current State' for simplicity 
-- or can be extended to hold multiple rows per employee_id if historical snapshots are required.
-- Here we design for a 'Current State' view optimized for reporting.

CREATE TABLE IF NOT EXISTS employees.employee_facts (
    id bigint NOT NULL, -- Surrogate/Primary Key
    first_name character varying(14) COLLATE pg_catalog."default" NOT NULL,
    last_name character varying(16) COLLATE pg_catalog."default" NOT NULL,
    gender character varying(10) COLLATE pg_catalog."default" NOT NULL,
    birth_date date NOT NULL,
    hire_date date NOT NULL,
    dept_name character varying(40) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    current_title character varying(50) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    current_salary bigint NOT NULL, -- Absorbed
    CONSTRAINT employees_employee_facts_pkey PRIMARY KEY (id),
    CONSTRAINT employees_employee_facts_dept_check CHECK (dept_name IS NOT NULL),
    CONSTRAINT employees_employee_facts_salary_check CHECK (current_salary IS NOT NULL)
);

-- Indexes for Employee Facts
CREATE INDEX IF NOT EXISTS idx_employee_facts_hire_date ON employees.employee_facts(hire_date);
CREATE INDEX IF NOT EXISTS idx_employee_facts_gender ON employees.employee_facts(gender);
CREATE INDEX IF NOT EXISTS idx_employee_facts_dept_name ON employees.employee_facts(dept_name);

-- 2. Department Fact Table (Wide)
-- Contains: Department attributes repeated for every employee/manager record
-- This replaces the separate 'department' table.

CREATE TABLE IF NOT EXISTS employees.department_facts (
    id character(4) COLLATE pg_catalog."default" NOT NULL,
    dept_name character varying(40) COLLATE pg_catalog."default" NOT NULL,
    CONSTRAINT employees_department_facts_pkey PRIMARY KEY (id),
    CONSTRAINT employees_department_facts_check CHECK (dept_name IS NOT NULL)
);

-- Indexes for Department Facts
CREATE INDEX IF NOT EXISTS idx_dept_facts_name ON employees.department_facts(dept_name);

-- 3. Employee-Department Relationship Fact Table (Denormalized)
-- Contains: Employee ID, Dept ID, Dates. 
-- We absorb 'dept_name' here too to avoid joining department_facts.

CREATE TABLE IF NOT EXISTS employees.department_employee_facts (
    employee_id bigint NOT NULL,
    department_id character(4) COLLATE pg_catalog."default" NOT NULL,
    from_date date NOT NULL,
    to_date date NOT NULL,
    dept_name character varying(40) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    CONSTRAINT employees_dept_emp_facts_pkey PRIMARY KEY (employee_id, department_id),
    CONSTRAINT employees_dept_emp_facts_dept_check CHECK (dept_name IS NOT NULL)
);

-- Indexes
CREATE INDEX IF NOT EXISTS idx_dept_emp_facts_emp_id ON employees.department_employee_facts(employee_id);
CREATE INDEX IF NOT EXISTS idx_dept_emp_facts_dept_name ON employees.department_employee_facts(dept_name);

-- 4. Employee-Manager Relationship Fact Table (Denormalized)
-- Contains: Employee ID, Dept ID, Dates, Absorbed Dept Name.

CREATE TABLE IF NOT EXISTS employees.department_manager_facts (
    employee_id bigint NOT NULL,
    department_id character(4) COLLATE pg_catalog."default" NOT NULL,
    from_date date NOT NULL,
    to_date date NOT NULL,
    dept_name character varying(40) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    CONSTRAINT employees_dept_mgr_facts_pkey PRIMARY KEY (employee_id, department_id),
    CONSTRAINT employees_dept_mgr_facts_dept_check CHECK (dept_name IS NOT NULL)
);

-- Indexes
CREATE INDEX IF NOT EXISTS idx_dept_mgr_facts_emp_id ON employees.department_manager_facts(employee_id);
CREATE INDEX IF NOT EXISTS idx_dept_mgr_facts_dept_name ON employees.department_manager_facts(dept_name);

-- 5. Salary Fact Table (Denormalized)
-- Contains: Employee ID, Salary Amount, Dates, Absorbed Employee Info.

CREATE TABLE IF NOT EXISTS employees.salary_facts (
    employee_id bigint NOT NULL,
    amount bigint NOT NULL,
    from_date date NOT NULL,
    to_date date NOT NULL,
    first_name character varying(14) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    last_name character varying(16) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    gender character varying(10) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    CONSTRAINT employees_salary_facts_pkey PRIMARY KEY (employee_id, from_date),
    CONSTRAINT employees_salary_facts_emp_check CHECK (first_name IS NOT NULL)
);

-- Indexes
CREATE INDEX IF NOT EXISTS idx_salary_facts_amount ON employees.salary_facts(amount);
CREATE INDEX IF NOT EXISTS idx_salary_facts_year ON employees.salary_facts(EXTRACT(YEAR FROM from_date));

-- 6. Title Fact Table (Denormalized)
-- Contains: Employee ID, Title, Dates, Absorbed Employee Info.

CREATE TABLE IF NOT EXISTS employees.title_facts (
    employee_id bigint NOT NULL,
    title character varying(50) COLLATE pg_catalog."default" NOT NULL,
    from_date date NOT NULL,
    to_date date NOT NULL,
    first_name character varying(14) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    last_name character varying(16) COLLATE pg_catalog."default" NOT NULL, -- Absorbed
    CONSTRAINT employees_title_facts_pkey PRIMARY KEY (employee_id, title, from_date),
    CONSTRAINT employees_title_facts_emp_check CHECK (first_name IS NOT NULL)
);

-- Indexes
CREATE INDEX IF NOT EXISTS idx_title_facts_title ON employees.title_facts(title);
CREATE INDEX IF NOT EXISTS idx_title_facts_year ON employees.title_facts(EXTRACT(YEAR FROM from_date));
```
