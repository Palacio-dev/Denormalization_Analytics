### Analysis and Redesign Strategy

The provided schema represents a classic normalized relational model (likely in 3NF) designed for transactional integrity and 
ACID compliance. However, for analytical workloads (BI dashboards, historical reporting), this structure suffers from high join 
complexity and data redundancy in time-series aggregations.

#### 1. Structural Analysis & Decisions

**Current Issues:**
- **Star Schema Mismatch:** The `ANO` table attempts to link multiple dimensions (`IES`, `MUNICIPIO`, `UF`, `CURSO`, `ENADE`, `SAEB`, `IDEB`) via a single row per year. This creates a massive "bridge" table that forces every analytical query to join 7+ tables to get basic metrics.
- **Dimension Redundancy:** `UF`, `MUNICIPIO`, `IES`, and `ESCOLA` contain repeating attributes (names, codes) that are duplicated in `ANO`.
- **Fact Table Overlap:** `ENADE`, `SAEB`, and `IDEB` tables are currently standalone facts without an explicit "event" or "metric" table to capture the volume of data (e.g., number of students, scores) associated with specific entities.

**Redesign Strategy (Star Schema):**
We will adopt a standard **Star Schema** optimized for SQL Server/PostgreSQL (compatible with the `IDENTITY` constraints provided).

1.  **Fact Table (`FATO_ESCOLA_ACADEMICO`)**:
    -   This will be the central hub. Instead of having a separate `ANO` table, the year will be a column directly in the fact table.
    -   We will include the primary keys of the dimensions as foreign keys.
    -   Measures will be added directly here (e.g., `qtd_inscritos`, `qtd_concluintes`, `media_ideb`, etc.) to avoid joining back to dimension tables for metrics.

2.  **Dimension Tables**:
    -   **`DIM_UNIDADE_FED`**: Consolidated `UF` and `MUNICIPIO` (if needed, though usually kept separate for hierarchy). We will keep them separate but ensure they are lightweight.
    -   **`DIM_ESCOLA`**: Consolidated `ESCOLA` and `IES` logic if they share attributes, but since they are distinct entities, we will create a unified `DIM_ESCOLA` that holds the school info and a link to the institution, or keep them slightly denormalized if the hierarchy is deep. *Decision*: Let's create `DIM_ESCOLA` which holds school details and `DIM_INSTITUCAO` for IES details to keep the fact table clean.
    -   **`DIM_CURSO`**: Holds course info.
    -   **`DIM_ANO`**: A dedicated dimension table for years to allow filtering by year ranges easily.

3.  **Denormalization of Metrics**:
    -   Instead of joining `FATO` to `ENADE` to get `nota_bruta_ce`, we assume the `FATO` table will store the calculated metrics for that specific year/school combination (e.g., `media_ideb_2023`, `qtd_inscritos_enade_2023`). This is a critical denormalization step for performance.

#### 2. Attribute-Level Changes

-   **Derived Attributes**: Added columns like `ano_escolar` (calculated from year) and `tipo_instituicao` (derived from `rede`).
-   **Removed Attributes**: Removed `id_enade`, `id_saeb`, `id_ideb` from the fact table if the source tables are small, but given the requirement for analytical queries, it is safer to store the *metrics* in the fact table and reference the *metadata* (like the specific ENADE year ID) in the dimension table.
-   **Consolidated Attributes**: `sigla_uf` and `nome_uf` moved to `DIM_UNIDADE_FED`. `nome_escola` and `cod_escola` moved to `DIM_ESCOLA`.

#### 3. Trade-offs

-   **Write Performance**: Inserting into the Fact table requires pre-calculating aggregates (e.g., summing all students for a school in a year). This adds complexity to the ETL process but drastically improves read speed.
-   **Data Freshness**: If the source tables (`ENADE`, `SAEB`) change, the Fact table must be updated. We assume an incremental load strategy.
-   **Storage**: The denormalized schema will be larger due to repeated dimension data in the fact table, but this is acceptable for the query performance gain.
