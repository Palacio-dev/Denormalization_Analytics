# Principal Data Architect Analysis: From OLTP to OLAP

## Phase 1 – Schema Assessment

**Entity Relationships & Cardinalities:**
The source schema represents a classic "Factless Dimension" scenario common in retail and media analytics, combined with a hierarchical employee structure.
1.  **Customer (Factless Dimension):** Linked to `Invoice`. Contains rich demographic and contact data.
2.  **Employee (Factless Dimension):** Linked to `Customer` (Support Rep) and `Employee` (Reporting). Hierarchical structure (`ReportsTo`).
3.  **Album (Dimension):** Linked to `Artist` and `Track`.
4.  **Artist (Dimension):** Lookup table.
5.  **Track (Fact/Dimension Hybrid):** The core transactional entity for sales (`InvoiceLine` references `Track`). Contains attributes like `Milliseconds`, `Bytes`, `UnitPrice`.
6.  **Invoice (Fact Table):** The primary transaction record. Contains `Total`, `InvoiceDate`, `CustomerId`.
7.  **InvoiceLine (Fact Detail):** The atomic transaction line item.
8.  **Genre, MediaType, Playlist (Dimensions):** Attribute tables for classification.
9.  **Playlist (Dimension):** Linked to `Track` via `PlaylistTrack`.

**Query Access Patterns:**
Analytical workloads on this schema typically involve:
*   **Time-Series Aggregation:** Summing sales (`Total`) by `InvoiceDate` (Month/Year), grouped by `CustomerId` or `City`.
*   **Product Analytics:** Calculating average `UnitPrice` or `Bytes` per `Genre`, `MediaType`, or `Artist`.
*   **Customer Profiling:** Aggregating total spend per `Customer`, joined with `FirstName`/`LastName`/`Company`.
*   **Hierarchy Analysis:** Summing sales per `Employee` up the chain to `ReportsTo` (e.g., Regional Manager).
*   **Catalog Exploration:** Counting tracks per `Album`, joined with `Genre` and `MediaType`.

**Key Challenges:**
*   **Join Complexity:** A standard query to get "Total sales by Artist" requires joining `Invoice` -> `InvoiceLine` -> `Track` -> `Album` -> `Artist`. This is 4-5 joins.
*   **Factless Dimensions:** `Customer` and `Employee` tables have no facts but are frequently joined to enrich `Invoice` or `Track` data.
*   **Redundant Attributes:** Address, City, State, Country are repeated in `Customer`, `Invoice`, and `Employee`.

## Phase 2 - Analytical Modeling Strategy

**Chosen Architecture: Star Schema with Wide Dimensions**

**Justification:**
1.  **Query Simplicity:** OLAP workloads suffer significantly from join depth. A Star Schema minimizes joins by embedding dimension attributes directly into the Fact tables (or creating very wide Dimension tables).
2.  **BI Compatibility:** Tools like Tableau, PowerBI, and Looker prefer Star Schemas for intuitive drill-downs. The "Album" and "Track" entities often act as the central hub for product metrics.
3.  **Read Performance:** Denormalizing `Customer` and `Employee` attributes into the `Invoice` and `InvoiceLine` (or a dedicated `CustomerFact` table) allows for immediate filtering and grouping without expensive joins.
4.  **Handling Factless Dimensions:** Since `Customer` and `Employee` do not have native facts, we will create **Factless Dimension Tables** that are joined to the main Fact tables (`Invoice`, `Track`). Alternatively, for maximum denormalization, we can embed key customer/employee attributes into the Fact tables, but given the volume of data, dedicated Factless Dimension tables with clustering are often more maintainable for large datasets. *Decision: We will adopt a hybrid approach where `Invoice` is heavily denormalized with Customer details, and `Track` is heavily denormalized with Album/Genre details, while keeping `Employee` as a separate Factless Dimension table optimized for hierarchy queries.*

**Specific Denormalization Decisions:**

1.  **Customer Data Absorption:**
    *   *Decision:* Move `FirstName`, `LastName`, `Company`, `City`, `State`, `Country`, `PostalCode` from the `Customer` table into the `Invoice` table.
    *   *Objective:* Eliminate the join between `Invoice` and `Customer` for 90% of analytical queries.
    *   *Redundancy:* High. Customer info is repeated per invoice.
    *   *Maintenance:* Requires an ETL process to keep `Invoice.CustomerId` and `Invoice.CustomerFirstName` synchronized.

2.  **Track Attribute Expansion:**
    *   *Decision:* Create a `Track` table that includes `AlbumName`, `ArtistName`, `GenreName`, `MediaTypeName`, `AlbumArtistId`, `GenreId`, `MediaTypeId`.
    *   *Objective:* Allow queries like "Sum of Bytes per Genre" without joining `Track` -> `Album` -> `Artist` -> `Genre`.
    *   *Redundancy:* Medium. Album and Artist names are repeated for every track.

3.  **Employee Hierarchy Preservation:**
    *   *Decision:* Keep `Employee` as a standalone table but add a `ManagerName` column (derived or stored) to flatten the hierarchy for reporting. Alternatively, create a `SalesRep` fact table if specific reps are assigned to specific regions. For this schema, we will create a `Employee` table that is joined to `Invoice` via `SupportRepId` but also denormalize `City`, `State`, `Country` into `Invoice` where applicable.
    *   *Refined Decision:* Given the `ReportsTo` hierarchy, it is best to keep `Employee` as a dimension but ensure `Invoice` includes `SupportRepName` and `SupportRepCity` for flat reporting.

4.  **Playlist Integration:**
    *   *Decision:* Since `Playlist` is often used for user behavior analysis, we will create a `Playlist` table that includes `TrackName`, `ArtistName`, `AlbumName` to facilitate "Top played songs" reports without joining back to `Track`.

**Tradeoffs:**
*   **Storage Growth:** Expect a 2x to 3x increase in storage due to repeated strings.
*   **Update Complexity:** Updating a customer's city requires updating `Customer` AND every `Invoice` linked to them. This is a critical maintenance risk in the ETL pipeline.
*   **Data Freshness:** Denormalized data is "stale" relative to the source of truth unless the ETL runs frequently.

## Phase 3 – Analytical Physical Model Design

### Optimized DDL Script

```sql
-- ==========================================
-- SECTION 1: DENORMALIZED DIMENSION & FACT TABLES
-- Architecture: Star Schema (Wide Dimensions)
-- ==========================================

-- 1. Core Fact Table: Invoice (Heavily Denormalized)
-- Includes Customer demographics, Invoice details, and Billing info.
CREATE TABLE IF NOT EXISTS public."Invoice" (
    "InvoiceId" integer NOT NULL,
    "CustomerId" integer NOT NULL,
    "InvoiceDate" timestamp without time zone NOT NULL,
    -- Denormalized Customer Attributes
    "CustomerFirstName" character varying(40) COLLATE pg_catalog."default" NOT NULL,
    "CustomerLastName" character varying(20) COLLATE pg_catalog."default" NOT NULL,
    "CustomerCompany" character varying(80) COLLATE pg_catalog."default",
    "CustomerCity" character varying(40) COLLATE pg_catalog."default",
    "CustomerState" character varying(40) COLLATE pg_catalog."default",
    "CustomerCountry" character varying(40) COLLATE pg_catalog."default",
    "CustomerPostalCode" character varying(10) COLLATE pg_catalog."default",
    -- Denormalized Billing Attributes (Moved from Invoice to reduce join depth)
    "BillingCity" character varying(40) COLLATE pg_catalog."default",
    "BillingState" character varying(40) COLLATE pg_catalog."default",
    "BillingCountry" character varying(40) COLLATE pg_catalog."default",
    "BillingPostalCode" character varying(10) COLLATE pg_catalog."default",
    "Total" numeric(10, 2) NOT NULL,
    -- Foreign Key (Logical only, physical enforcement removed for OLAP flexibility)
    CONSTRAINT "PK_Invoice" PRIMARY KEY ("InvoiceId")
);

-- 2. Fact Table: InvoiceLine (Denormalized Track & Genre)
-- Includes Track metadata to avoid joins with Track/Album/Genre tables.
CREATE TABLE IF NOT EXISTS public."InvoiceLine" (
    "InvoiceLineId" integer NOT NULL,
    "InvoiceId" integer NOT NULL,
    -- Denormalized Track Attributes
    "TrackName" character varying(200) COLLATE pg_catalog."default" NOT NULL,
    "TrackArtistName" character varying(120) COLLATE pg_catalog."default",
    "TrackAlbumName" character varying(160) COLLATE pg_catalog."default",
    "TrackGenreName" character varying(120) COLLATE pg_catalog."default",
    "TrackMediaTypeName" character varying(120) COLLATE pg_catalog."default",
    "TrackMilliseconds" integer NOT NULL,
    "TrackBytes" integer,
    "TrackUnitPrice" numeric(10, 2) NOT NULL,
    -- Original FKs kept for reference but not enforced strictly in OLAP
    CONSTRAINT "PK_InvoiceLine" PRIMARY KEY ("InvoiceLineId")
);

-- 3. Factless Dimension: Employee (Optimized for Hierarchy)
-- Added ManagerName to flatten hierarchy for reporting.
CREATE TABLE IF NOT EXISTS public."Employee" (
    "EmployeeId" integer NOT NULL,
    "LastName" character varying(20) COLLATE pg_catalog."default" NOT NULL,
    "FirstName" character varying(20) COLLATE pg_catalog."default" NOT NULL,
    "Title" character varying(30) COLLATE pg_catalog."default",
    "ReportsTo" integer,
    "ManagerName" character varying(20) COLLATE pg_catalog."default", -- Derived/Flattened
    "BirthDate" timestamp without time zone,
    "HireDate" timestamp without time zone,
    -- Address fields moved to Invoice for flat reporting, 
    -- but kept here for employee-specific reports.
    "City" character varying(40) COLLATE pg_catalog."default",
    "State" character varying(40) COLLATE pg_catalog."default",
    "Country" character varying(40) COLLATE pg_catalog."default",
    "PostalCode" character varying(10) COLLATE pg_catalog."default",
    "Phone" character varying(24) COLLATE pg_catalog."default",
    "Fax" character varying(24) COLLATE pg_catalog."default",
    "Email" character varying(60) COLLATE pg_catalog."default",
    CONSTRAINT "PK_Employee" PRIMARY KEY ("EmployeeId")
);

-- 4. Factless Dimension: Customer (Backup for complex joins)
-- In a pure Star schema, Customer attributes are in Invoice. 
-- We keep this minimal to avoid redundancy unless specific Customer-only reports are needed.
CREATE TABLE IF NOT EXISTS public."Customer" (
    "CustomerId" integer NOT NULL,
    "FirstName" character varying(40) COLLATE pg_catalog."default" NOT NULL,
    "LastName" character varying(20) COLLATE pg_catalog."default" NOT NULL,
    "Company" character varying(80) COLLATE pg_catalog."default",
    "Address" character varying(70) COLLATE pg_catalog."default",
    "City" character varying(40) COLLATE pg_catalog."default",
    "State" character varying(40) COLLATE pg_catalog."default",
    "Country" character varying(40) COLLATE pg_catalog."default",
    "PostalCode" character varying(10) COLLATE pg_catalog."default",
    "Phone" character varying(24) COLLATE pg_catalog."default",
    "Fax" character varying(24) COLLATE pg_catalog."default",
    "Email" character varying(60) COLLATE pg_catalog."default" NOT NULL,
    "SupportRepId" integer,
    CONSTRAINT "PK_Customer" PRIMARY KEY ("CustomerId")
);

-- 5. Product Catalog Dimensions (Flattened into Track for performance)
-- We create a 'Track' table that acts as a dimension but includes all lookup names.
CREATE TABLE IF NOT EXISTS public."Track" (
    "TrackId" integer NOT NULL,
    "Name" character varying(200) COLLATE pg_catalog."default" NOT NULL,
    "AlbumId" integer,
    "ArtistId" integer,
    "GenreId" integer,
    "MediaTypeId" integer NOT NULL,
    "Composer" character varying(220) COLLATE pg_catalog."default",
    "Milliseconds" integer NOT NULL,
    "Bytes" integer,
    "UnitPrice" numeric(10, 2) NOT NULL,
    -- Lookup Attributes (Flattened)
    "AlbumName" character varying(160) COLLATE pg_catalog."default",
    "ArtistName" character varying(120) COLLATE pg_catalog."default",
    "GenreName" character varying(120) COLLATE pg_catalog."default",
    "MediaTypeName" character varying(120) COLLATE pg_catalog."default",
    CONSTRAINT "PK_Track" PRIMARY KEY ("TrackId")
);

-- 6. Playlist Dimension (Flattened)
CREATE TABLE IF NOT EXISTS public."Playlist" (
    "PlaylistId" integer NOT NULL,
    "Name" character varying(120) COLLATE pg_catalog."default",
    "TrackName" character varying(200) COLLATE pg_catalog."default",
    "TrackArtistName" character varying(120) COLLATE pg_catalog."default",
    "TrackAlbumName" character varying(160) COLLATE pg_catalog."default",
    CONSTRAINT "PK_Playlist" PRIMARY KEY ("PlaylistId")
);

-- ==========================================
-- SECTION 2: OPTIMIZED INDEXES & CLUSTERING
-- ==========================================

-- Partitioning Recommendation: 
-- For Invoice and InvoiceLine, partition by date (InvoiceDate) is critical for time-series analytics.
ALTER TABLE public."Invoice"
    ADD PARTITION BY RANGE ( "InvoiceDate" );

ALTER TABLE public."InvoiceLine"
    ADD PARTITION BY RANGE ( "InvoiceDate" );

-- Create Clusters for Hot Data
-- Cluster Invoice by Date and Customer for fast aggregation
CREATE CLUSTER ON public."Invoice" ( "InvoiceDate", "CustomerId" );

-- Cluster InvoiceLine by Date and TrackName for fast product analytics
CREATE CLUSTER ON public."InvoiceLine" ( "InvoiceDate", "TrackName" );

-- ==========================================
-- SECTION 3: REMOVED/FLATTENED FOREIGN KEY CONSTRAINTS
-- Note: In OLAP, physical FK constraints are often removed to allow 
-- data independence and faster writes, relying on ETL logic instead.
-- ==========================================

-- Removed FK constraints to allow flexible data loading and denormalization
-- (FKs are logical, not physical, in this optimized model)

-- ==========================================
-- SECTION 4: ANALYTICAL METRICS VIEWS (Optional but Recommended)
-- ==========================================

-- View: Top Artists by Revenue
CREATE VIEW public."v_ArtistRevenue" AS
SELECT 
    "TrackArtistName",
    COUNT(*) AS "TrackCount",
    SUM("TrackUnitPrice" * 1) AS "EstimatedRevenue"
FROM public."InvoiceLine"
GROUP BY "TrackArtistName"
ORDER BY "EstimatedRevenue" DESC;

-- View: Monthly Sales by Region
CREATE VIEW public."v_MonthlySalesRegion" AS
SELECT 
    DATE_TRUNC('month', "InvoiceDate") AS "Month",
    "CustomerCity",
    "CustomerState",
    COUNT(*) AS "InvoiceCount",
    SUM("Total") AS "TotalRevenue"
FROM public."Invoice"
GROUP BY DATE_TRUNC('month', "InvoiceDate"), "CustomerCity", "CustomerState";

```
