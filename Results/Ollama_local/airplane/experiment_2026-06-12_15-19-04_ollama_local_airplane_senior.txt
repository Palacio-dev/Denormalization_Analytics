# Principal Data Architect Analysis: Airline Analytics Platform Transformation

## Phase 1 – Schema Assessment

### Entity Relationships & Cardinalities
The source schema exhibits a classic **OLTP (Online Transaction Processing)** design with normalized entities to ensure data integrity and minimize storage during write operations.
- **Fact Entities**: `bookings` (transactional events), `boarding_passes` (assignment events), `ticket_flights` (pricing/segment events).
- **Dimension Entities**: `aircrafts_data`, `airports_data`, `flights`, `seats`, `tickets`.
- **Relationships**:
    - `tickets` $\leftrightarrow$ `bookings` (1:1)
    - `tickets` $\leftrightarrow$ `ticket_flights` (1:1)
    - `ticket_flights` $\leftrightarrow$ `flights` (1:1)
    - `boarding_passes` $\leftrightarrow$ `ticket_flights` (1:1)
    - `flights` $\leftrightarrow$ `aircrafts_data` (1:1)
    - `flights` $\leftrightarrow$ `airports_data` (1:N via departure/arrival)
    - `seats` $\leftrightarrow$ `flights` (1:N via aircraft_code, though `seats` is defined per aircraft/seat, not per flight; this implies a static seat map per aircraft type).

### Query Access Patterns
Analytical workloads for this domain typically involve:
1.  **Global Aggregations**: Total revenue by region, flight status distribution, load factor by aircraft type.
2.  **Temporal Analysis**: Revenue per day, booking trends over time.
3.  **Geospatial Analysis**: Flight paths, airport connectivity, city-level demand.
4.  **Complex Joins**: Calculating revenue per passenger, combining seat availability with flight schedules and aircraft specs.

**Current Bottleneck**: Queries requiring these metrics must perform multiple nested joins (e.g., `bookings` $\to$ `tickets` $\to$ `ticket_flights` $\to$ `flights` $\to$ `aircrafts`/`airports`). In a columnar OLAP engine (like ClickHouse, Snowflake, or Redshift), this creates high I/O overhead and limits the ability to push down filters.

## Phase 2 - Analytical Modeling Strategy

### Chosen Architecture: **Star Schema with Wide Dimension Tables**
**Justification**:
1.  **Read-Optimized**: The goal is to maximize query speed for aggregations. A star schema minimizes join operations, allowing the query optimizer to filter on fact tables before joining dimensions.
2.  **BI Compatibility**: Most BI tools (Tableau, PowerBI, Looker) perform best with a single central fact table and wide dimensions.
3.  **Complexity Reduction**: The `ticket_flights` table acts as a critical junction for pricing and segments. Absorbing `flight_id` into `tickets` and `aircraft_code` into `seats` (where appropriate) reduces join depth from 4-5 to 1-2.

### Denormalization Decisions

| Decision ID | Description | Performance Objective | Join Reduction | Redundancy | Maintenance Implication |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **D1** | **Flatten `tickets`**: Add `flight_id` and `aircraft_code` directly to `tickets`. | Eliminates the need to join `tickets` $\to$ `ticket_flights` $\to$ `flights` for basic passenger/flight context. | Reduces join count by 2. | `flight_id` and `aircraft_code` are duplicated in `tickets`. | Requires update on `ticket_flights` to propagate changes to `tickets` (or accept stale data if using a snapshot model). |
| **D2** | **Absorb `seats` into `flights`**: Create a `flight_segments` table containing `flight_id`, `aircraft_code`, `seat_no`, `fare_conditions`. | Allows direct aggregation of seat capacity and pricing per flight without joining the static `seats` table. | Reduces join count by 1. | `seats` table becomes redundant. | `seats` table is no longer needed for active analytics. |
| **D3** | **Wide `flights`**: Include `aircraft_code`, `departure_airport_code`, `arrival_airport_code`, `status` in the main fact table (or a dedicated `flight_info` dimension joined once). | Enables filtering by aircraft type or route status without joining multiple dimension tables. | Reduces join count by 2. | Repeats airport codes and aircraft codes. | Minimal impact; data is read-heavy, not write-heavy. |
| **D4** | **Reference Data Absorption**: Create `airport_info` and `aircraft_info` tables with full details (name, city, coordinates, model) to replace lookups. | Enables direct filtering on airport names or aircraft models without joining the small lookup tables. | Reduces join count by 2. | High redundancy of text/coordinates. | Negligible; updates are rare for reference data. |

## Phase 3 – Analytical Physical Model Design

The following schema is designed for a columnar store (e.g., PostgreSQL with hypertables, Snowflake, or ClickHouse). It prioritizes **query throughput** over **write atomicity**.

### Key Design Choices:
- **Partitioning**: `bookings`, `tickets`, and `ticket_flights` are partitioned by `book_date` (or `created_at`) to enable efficient pruning of historical data.
- **Clustering**: `tickets` and `ticket_flights` are clustered by `ticket_no` to speed up passenger-centric queries.
- **Data Types**: `JSONB` is retained for unstructured data (contact info, model details) to avoid rigid schema changes, but critical fields are normalized.
- **Surrogate Keys**: `ticket_no` is used as the natural key (PK) across the denormalized core.

);

);

CREATE TABLE IF NOT EXISTS bookings.bookings_2023 PARTITION OF bookings.bookings

### Summary of Tradeoffs
1.  **Storage Growth**: We have increased storage requirements due to duplicating `flight_id`, `aircraft_code`, and `seat_no` in the `tickets` and `ticket_flights` tables. However, this is a standard tradeoff in data warehousing to gain query performance.
2.  **Update Latency**: If a flight changes its aircraft type, the `flights` table must be updated, and potentially the `tickets` table if it was denormalized to include the specific flight's aircraft (though usually, the aircraft type is static per flight). In a strict OLTP environment, this requires careful handling; in an OLAP environment, we often accept a slight lag or use a "snapshot" approach where `tickets` are loaded at a specific point in time.
3.  **Traceability**: The primary key `ticket_no` remains the anchor across `tickets`, `ticket_flights`, and `boarding_passes`, ensuring full traceability of a passenger's journey even without complex joins.
