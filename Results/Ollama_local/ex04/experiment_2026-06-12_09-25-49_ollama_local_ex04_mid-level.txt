### Analysis and Redesign Strategy

#### Section 1: Schema Analysis and Denormalization Strategy

**1. Analysis of Current Structure**
The provided schema is a classic **Third Normal Form (3NF)** design. It separates data into distinct entities:
*   **Dimensions:** `country`, `region`, `demography`, `employment`, `education`, `economy`, `health`, `survey`.
*   **Facts (Implicit):** Tables like `survey`, `demography`, `employment`, etc., act as fact tables but are highly normalized (e.g., `demography` has `year` and `country_code` as separate columns without a composite key linking them tightly to specific measures).
*   **Granularity Issues:** The `demography`, `employment`, `education`, and `economy` tables lack a unified time-series dimension key. Queries requiring year-over-year analysis across multiple domains require joining these disparate fact tables on `(year, country_code)`, which is inefficient.
*   **Join Complexity:** A typical dashboard query (e.g., "GDP vs. Unemployment vs. Education for 2020") requires joining 6+ tables, resulting in significant latency and potential cardinality explosion issues during aggregation.

**2. Structural Decisions**
To optimize for read-heavy workloads, we will adopt a **Star Schema** with a highly denormalized **Fact Table** approach.

*   **Decision D1: Create a Unified `fact_country_indicators` Table.**
    *   Instead of multiple normalized fact tables, we consolidate `survey`, `demography`, `employment`, `education`, `economy`, and `health` into a single massive fact table.
    *   **Rationale:** This eliminates the need for `JOIN`s on `(year, country_code)` for almost all analytical queries. The table becomes the single source of truth for country-level metrics.
*   **Decision D2: Denormalize Dimensions into the Fact Table.**
    *   Move `country_code`, `region_code`, `survey_acronym`, and `year` directly into the fact table.
    *   **Rationale:** Since the grain is effectively "Country-Year-Indicator", repeating these dimensions in the fact table avoids the join overhead.
*   **Decision D3: Handle Region Hierarchy.**
    *   Since `region_code` is foreign to `country_code`, we include `region_code` in the fact table. If a country has multiple regions, the data will be repeated (one row per country-region-year-indicator combination), which is acceptable for analytical reporting unless region-level granularity is strictly required.
*   **Decision D4: Flatten Demographic and Health Dimensions.**
    *   The `demography` and `life_expectancy` tables currently link via `id_demography`. We flatten this by embedding `gender`, `pop_density`, etc., directly into the fact table rows, indexed by `country_code` and `year`.

**3. Attribute-Level Changes**
*   **Decision A1: Add `year` and `country_code` to all indicator columns.**
    *   Currently, `demography` has `year` and `country_code` but `employment` does not (it has `id_employment` which implies a unique ID but not necessarily a composite key of year/country). We standardize the grain to `Country-Year-Indicator`.
*   **Decision A2: Remove Foreign Keys from Fact Table.**
    *   The new `fact_country_indicators` table will not have foreign keys pointing to dimension tables. It stands alone.
*   **Decision A3: Add Derived/Calculated Columns.**
    *   Add `region_name` directly if not present, or keep `region_code` if the mapping is 1:1. We will assume 1:1 for simplicity in this denormalization unless specified otherwise, repeating `region_name` in the fact table.

**4. Trade-offs**
*   **Tradeoff T1: Storage vs. Query Speed.**
    *   *Impact:* The denormalized table will be significantly larger in size than the sum of the original normalized tables due to data repetition (especially for countries with multiple regions or demographic breakdowns).
    *   *Mitigation:* Use appropriate columnar storage formats (e.g., Parquet, Delta Lake) or compression.
*   **Tradeoff T2: Data Integrity Constraints.**
    *   *Impact:* Removing foreign keys reduces the ability to enforce referential integrity at the database level (e.g., preventing a "survey" from referencing a non-existent country).
    *   *Mitigation:* Rely on application-layer validation and data quality pipelines (e.g., Great Expectations) rather than SQL constraints.
*   **Tradeoff T3: Update Complexity.**
    *   *Impact:* Updating a single country's GDP affects only one row in the new schema, which is good. However, if we previously had a separate `economy` table, the update logic is simpler, but the schema design itself is more rigid regarding the grain.
