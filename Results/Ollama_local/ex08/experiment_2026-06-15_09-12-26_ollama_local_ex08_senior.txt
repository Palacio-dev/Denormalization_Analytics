# Principal Data Architect Analysis: OLTP to OLAP Transformation

## Phase 1 – Schema Assessment

### Entity Relationships & Cardinalities
The source schema represents a classic **Transactional OLTP** design with a 1:N and N:M relationship structure:
1.  **Aluno (Student)**: 1:N with `Matricula` (One student, many enrollments).
2.  **Curso (Course)**: 1:N with `Matricula` (One course, many enrollments).
3.  **Escola (School)**: 1:N with `Matricula`, `Desempenho_ENEM`, `Indicadores`, `Participacao_ENEM`.
4.  **Localizacao (Location)**: 1:N with `Escola`, `Vinculo`.
5.  **Vinculo (Employment)**: N:M relationships with `Aluno` and `Remuneracao` (Many students/years, many salary records).
6.  **Remuneracao (Salary)**: 1:N with `Vinculo`.

### Join Paths & Access Patterns
In a reporting environment, the primary query pattern is the **Student Lifecycle Analysis**:
`Aluno` $\to$ `Matricula` $\to$ `Curso` $\to$ `Escola` $\to$ `Indicadores` / `Participacao_ENEM` / `Desempenho_ENEM`.

Currently, this requires **5 to 6 table joins** per student record.
-   **Lookup Tables**: `Curso`, `Escola`, `Localizacao` are small reference tables.
-   **Fact Tables**: `Matricula`, `Desempenho_ENEM`, `Indicadores`, `Participacao_ENEM`, `Vinculo` contain the transactional data.
-   **Dimensions**: `Aluno`, `Remuneracao`.

### Architectural Strategy: Hybrid Star Schema
Given the mix of granular transactional data (enrollments, individual performance) and aggregated metrics (school indicators), a pure Star Schema is insufficient. We will adopt a **Hybrid Dimensional Model**:
1.  **Fact Tables**: Will be denormalized into wide tables containing all dimension attributes (School, Course, Location, Student demographics) directly in the fact row to eliminate joins.
2.  **Dimension Tables**: Will be collapsed into the facts where possible, but kept distinct for `Remuneracao` and `Curso` if they have complex filtering logic (though in this schema, they are relatively flat).
3.  **Reference Data Absorption**: Attributes like `co_escola_educacenso`, `nu_ano`, and `co_curso` will be promoted from foreign keys to primary columns in the fact tables.

**Justification**:
-   **Performance**: Eliminates the "Join Explosion" common in BI tools (e.g., Tableau, PowerBI, Superset) when querying `Aluno` $\to$ `Escola` $\to$ `Indicadores`.
-   **Scalability**: Aggregations over `Indicadores` and `Participacao` can be pre-calculated or run efficiently on wide tables without needing to join back to `Escola`.
-   **Traceability**: We maintain a `source_id` column in each new table to allow auditing back to the original `id_aluno` or `co_escola` if data quality issues arise.

## Phase 2 - Analytical Modeling Strategy

### Decision: Wide Fact Tables (Denormalized)
Instead of keeping `matricula_ifb` as a narrow fact with separate dimension tables, we will expand it to include all necessary attributes for a standard "Student Performance Report".

**Performance Objective**:
Reduce query execution time by removing the need to join 4-5 tables for a single student's profile. This allows the database engine to perform row-level scans and aggregate immediately without I/O overhead from joining large dimension tables.

**Join Reduction**:
-   **Current**: 1 student query = 1 JOIN (matricula) + 4 JOINs (aluno, curso, escola, localizacao) + 3 JOINs (indicadores, etc.) = ~6-7 joins.
-   **Target**: 1 student query = 0-1 JOIN (if using a dedicated fact table per domain) or 0 joins if using a single super-fact table. We will create **3 specialized wide fact tables** to balance granularity and storage.

**Data Redundancy**:
-   Student demographics (`data_nascimento`, `sexo`, etc.) will be repeated in every `matricula` record.
-   School info (`no_escola`, `co_escola`) will be repeated in every enrollment record.
-   *Mitigation*: This is acceptable for OLAP where reads >> writes. The overhead of storing duplicate strings is negligible compared to the CPU cost of joining.

**Update Implications**:
-   **Risk**: If a student's name changes, it must be updated in *all* their enrollment records.
-   **Solution**: Use **Surrogate Keys** for the fact table rows, but keep the `source_id` (e.g., `id_aluno`) to ensure data integrity. We will implement a "Write-Once-Read-Many" philosophy for historical data; updates to student attributes should ideally happen at ingestion time or via a dedicated `student_master` table that drives the denormalized facts. For this transformation, we assume the data is relatively static or updates are batched.

### Decision: Aggregated Fact Tables
We will create specific tables for `Desempenho`, `Indicadores`, and `Participacao` that are already wide enough, but we will ensure they carry the `nu_ano` and `co_escola` as primary keys or leading columns to enable fast slicing.

## Phase 3 – Analytical Physical Model Design

The new schema consists of three core fact tables designed for slicing and dicing, plus a master dimension table for locations and a master for students to handle updates gracefully.

### Table Definitions

#### 1. `fact_matriculacao_estudante` (Wide Enrollment Fact)
*Replaces `matricula_ifb` by absorbing `aluno`, `curso`, and `escola` dimensions.*
-   **PK**: `id_matricula` (Surrogate)
-   **Foreign Keys**: `source_id_aluno`, `source_id_curso`, `source_id_escola` (for audit)
-   **Attributes**: All demographic data from `aluno`, course details from `curso`, school details from `escola`, and enrollment metadata.
-   **Partitioning**: By `ano` (Year of enrollment) to optimize time-series aggregation.
-   **Clustering**: By `source_id_escola` and `ano`.

#### 2. `fact_desempenho_academico` (Academic Performance Fact)
*Combines `desempenho_enem` and `indicadores_escolares` logic, linking to the school.*
-   **PK**: `id_desempenho` (Surrogate)
-   **Attributes**: ENEM scores, school indicators (retention, approval rate), school name/cod, year.
-   **Partitioning**: By `nu_ano`.
-   **Clustering**: By `nu_ano` and `co_escola_educacenso`.

#### 3. `fact_participacao_economica` (Economic/Participation Fact)
*Combines `participacao_enem` and `vinculo_empregaticio` logic.*
-   **PK**: `id_participacao` (Surrogate)
-   **Attributes**: Participation rates, employment data (salary, duration), student demographics, location data.
-   **Partitioning**: By `nu_ano`.
-   **Clustering**: By `nu_ano` and `source_id_aluno`.

#### 4. `dim_localizacao` (Master Location Dimension)
*Consolidated from `localizacao` and `escola` location refs.*
-   **PK**: `id_loc`
-   **Attributes**: UF, Municipio, State codes.
